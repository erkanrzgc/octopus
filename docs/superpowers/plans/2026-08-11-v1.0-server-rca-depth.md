# v1.0 depth data — Server-admin / Blue-team incident RCA reasoning

_2026-08-11 · plan-first (generate → measure → THEN retrain). Track #2 toward v1.0._

## Context
v0.9 is promoted (E1 payload-correctness 67→100%, persona 6/6, discovery 3/3). A retrain
**now** would be wasteful — v0.9 already consumed all current data. v1.0 only makes sense once
we add **new** depth. The thinnest trained domain is **server-admin / blue-team incident RCA**:
`data/sft/tools/server_blueteam_tr.jsonl` = **15 examples** (dpi_tr = 43). This is also where
Phase C was weakest.

Two X-post leads were evaluated (research-first, not drop-in):
- **OpenSRE** (Apache-2.0, tracer-cloud/opensre) — AI SRE agent. Its RCA loop is the pattern we
  teach: *fetch alert+correlated evidence → reason/hypothesize in a tool-calling loop →
  evidence-backed root cause → remediation → report.* Notably runs **scored synthetic RCA suites
  with adversarial red herrings** — a robustness idea we adopt. Pattern reference, no code port.
- **Agent-Reach** (MIT, Panniantong/Agent-Reach) — VERIFIED via README to be a **capability-layer /
  installer/router** (Jina Reader, yt-dlp, gh, Exa, feedparser), NOT a single tool. "Reading is done
  by the Agent calling upstream tools directly, no wrapper." So it does **not** fit our catalog as one
  extension tool (that would be fabrication). Its real value = a **B3 grounding-data engine** (run it →
  real web → grounded TR answers) — a separate, heavier track (needs install/run). **Deferred.**

## Goal
An SFT depth pack teaching **evidence-backed incident RCA reasoning** in Turkish, in the v0.9
`dusunce` (reasoning) + `arac` (tool-call) + tool-result multi-turn format. This is v1.0's headline
new capability: the model investigates a server/blue incident like an SRE — gathers evidence with
diagnostic tools **before** concluding, and links the root cause to that evidence.

## Scope — ~35–45 scenarios across incident classes
- Memory / OOM-killer; disk-full + inode exhaustion; runaway CPU / fork-bomb; service down /
  systemd crash-loop; slow DB query / connection-pool exhaustion; network latency / packet loss;
  TLS cert expiry; failed-auth / SSH brute-force spike (blue); config drift / bad deploy;
  log-flood filling disk; DNS resolution failure; permission / unit-file failure.
- **~6 adversarial "red-herring" cases** (a loud symptom that is NOT the root cause) — teaches the
  model to keep gathering evidence instead of latching onto the first signal.

## Format (match existing v0.9 multi-turn)
`system` (persona+tools) → `user` (alert/symptom, TR) → `assistant` (`dusunce` hypothesis + first
`arac` diagnostic call) → `tool` (realistic output) → `assistant` (narrow/next `arac`) → … →
`assistant` (evidence-backed **root cause + remediation**, no fabricated numbers).
Diagnostics via existing tools: `run_cmd` (journalctl/systemctl/ss/top/ps/df/dmesg/grep/dig) +
blue-server catalog tools (fail2ban/auditd/osquery/iptables). **Audit first**: prefer `run_cmd` for
shell diagnostics; add a catalog verb only if genuinely missing (avoid MASTER_TOOLS pollution).

## Quality gate (BEFORE spending money) — like the D1 gate
Mini held-out eval (free, local on octopus-v9 as baseline, then on v1.0):
1. **Evidence-before-conclusion**: model issues ≥1 `arac` diagnostic before asserting a root cause.
2. **Correct root cause** on N held-out scenarios (incl. ≥2 red-herrings).
3. **No fabricated tool output** (model doesn't invent log lines as if it ran them).
If weak → iterate the data. **Do NOT retrain on weak data** (would burn the $10 for a v0.9 clone).
